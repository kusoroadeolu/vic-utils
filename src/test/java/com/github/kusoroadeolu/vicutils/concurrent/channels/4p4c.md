# Concurrent Channel Benchmarks - 4P/4C

This document analyzes throughput benchmarks for different channel implementations under **balanced high contention** (4 producers, 4 consumers).

---

## Benchmark Setup

- **JMH version:** 1.37
- **JVM:** Java 25, HotSpot 64-Bit Server VM (25+37-LTS-3491)
- **Benchmark mode:** Throughput (ops/s)
- **Warmup:** 3 iterations × 5s each
- **Measurement:** 3 iterations × 5s each
- **Forks:** 3
- **Thread configuration:** 4 producers (platform threads) / 4 consumers (virtual threads)
- **Queue configuration:** Non-fair mode for ArrayBlockingQueue and SynchronousQueue

## Performance Analysis: What the Numbers Reveal

### The Million-ops Tier: Lock-Free Dominance

**SpinRendezvousChannel: 7.03M ops/s**
- Peak measurement: 8.4M ops/s (20% above average)
- Variance: ±827K ops/s (~12% coefficient of variation)
- Min/max spread: 2.0M ops/s

**What this tells us:**
- Pure CAS operations can handle 8 threads with minimal coordination overhead
- High variance (±1.4M confidence interval) suggests sensitivity to:
    - CPU scheduler decisions
    - Cache coherency protocols
    - Which producer/consumer pairs match up
- The 2M ops/s spread indicates real instability under load
- Still maintains throughput 2 orders of magnitude above lock-based approaches

**SynchronousQueue: 4.78M ops/s**
- Peak measurement: 5.27M ops/s (10% above average)
- Variance: ±367K ops/s (~8% coefficient of variation)
- Min/max spread: 1.1M ops/s

**What this tells us:**
- Dual-mode design (stack/queue) adds coordination overhead vs pure spinning
- **46% more stable** than SpinRendezvousChannel despite being 32% slower
- Internal parking/unparking costs ~2.2M ops/s vs pure spinning
- Sophisticated implementation trades peak performance for predictability
- Still 135× faster than best lock-based approach

### The Thousand-ops Tier: Lock-Based Reality

**ArrayBlockingQueue: 35.4K ops/s**
- Variance: ±2.6K ops/s (~7% coefficient of variation)
- Performance relative to SynchronousQueue: **135× slower**

**What this tells us:**
- Buffering + dual locks can't overcome fundamental synchronization costs
- Even with decades of JDK optimization, locks have inherent scaling limits
- Moderate variance despite low throughput indicates stable but slow execution
- Non-fair mode helps but can't break through ~40K ops/s ceiling

**RendezvousChannel: 23.1K ops/s**
- Variance: ±576 ops/s (~2.5% coefficient of variation)
- **Most stable implementation** despite being 304× slower than SpinRendezvousChannel

**What this tells us:**
- Triple condition variable coordination creates extreme overhead
- Single lock serializes all operations, creating natural stability
- Low variance shows predictable execution when everything waits its turn
- Box wrapper allocation adds measurable cost vs direct references
- Performance hit vs ABQ (35% slower) shows rendezvous coordination cost

**UnBufferedChannel: 15.9K ops/s**
- Variance: ±1.1K ops/s (~7% coefficient of variation)
- **Slowest overall** - 441× slower than SpinRendezvousChannel

**What this tells us:**
- `signalAll()` strategy creates measurable thundering herd overhead
- Less sophisticated than RendezvousChannel, resulting in 31% lower throughput
- Higher variance than RendezvousChannel suggests less efficient coordination
- Represents baseline lock-based performance without optimization

## Scaling from 1P-1C: How Contention Impacts Each Design

### Throughput Evolution Across Thread Counts

| Implementation | 1P-1C | 4P-2C | 4P-4C | Scaling Pattern |
|----------------|-------|-------|-------|-----------------|
| **SpinRendezvousChannel** | 5.49M | 6.56M | 7.03M | Positive scaling (+28%) |
| **SynchronousQueue** | 5.44M | 3.36M | 4.78M | Irregular scaling |
| **RendezvousChannel** | 111.7K | 22.1K | 23.1K | Severe degradation (-79%) |
| **ArrayBlockingQueue** | 101.9K | 54.5K | 35.4K | Linear degradation (-65%) |
| **UnBufferedChannel** | 73.7K | 15.6K | 15.9K | Severe degradation (-78%) |

### What These Patterns Tell Us

**SpinRendezvousChannel: Scales Up with Threads**
- 1P-1C → 4P-4C: +28% throughput improvement
- More threads = more parallelism = higher aggregate throughput
- CAS operations allow true concurrent progress
- Variance increases with threads (6% → 20%), showing coordination complexity

**SynchronousQueue: Optimizes for Balance**
- Best at 1P-1C (5.44M) and 4P-4C (4.78M)
- Worst at 4P-2C (3.36M) - imbalance hurts coordination
- Internal algorithm appears tuned for symmetric workloads
- Complex state machine has edge cases that hurt performance

**Lock-Based Channels: Hit Performance Ceiling**
- RendezvousChannel: 79% loss from 1P-1C to 4P-4C
- UnBufferedChannel: 78% loss from 1P-1C to 4P-4C
- Both stabilize around 15-23K ops/s regardless of configuration
- Single lock creates hard bottleneck that scales inversely with threads

**ArrayBlockingQueue: Predictable Linear Degradation**
- Each doubling of threads roughly halves throughput
- Dual-lock design delays but doesn't prevent scaling ceiling
- Buffer helps but can't overcome lock contention fundamentals
- Most predictable scaling pattern of all implementations

## Variance Analysis: The Throughput-Stability Tradeoff

### Coefficient of Variation at 4P-4C

| Implementation | CV | Absolute Variance | Interpretation |
|----------------|-----|-------------------|----------------|
| **RendezvousChannel** | ~2.5% | ±576 ops/s | Extremely stable |
| **UnBufferedChannel** | ~7% | ±1.1K ops/s | Moderately stable |
| **SynchronousQueue** | ~8% | ±367K ops/s | Good stability for speed |
| **ArrayBlockingQueue** | ~7% | ±2.6K ops/s | Stable |
| **SpinRendezvousChannel** | ~12% | ±827K ops/s | High variability |

### What Variance Patterns Reveal

**Lock-based channels: Low variance, low throughput**
- Serialization creates predictability
- Each operation waits in orderly queue
- Variance comes from minor timing differences, not coordination complexity
- Stability is side effect of bottleneck, not optimization

**Spin-based channels: High variance, high throughput**
- SpinRendezvousChannel: 827K ops/s variance (absolute)
- SynchronousQueue: 367K ops/s variance
- Coordination timing varies based on scheduler, cache coherency, thread pairing
- Higher throughput = more opportunities for variance to manifest

**The tradeoff:**
- RendezvousChannel: 2.5% variance, 23K throughput
- SpinRendezvousChannel: 12% variance, 7M throughput
- **5× variance penalty buys 304× throughput gain**

## Architectural Insights from 4P-4C Testing

### What Makes Lock-Free Fast?

**SpinRendezvousChannel at 7.03M ops/s:**
1. **No kernel involvement** - CAS operations are user-space only
2. **No context switches** - threads stay scheduled on cores
3. **Minimal cache coherency overhead** - single AtomicReference
4. **No fairness overhead** - first to CAS wins
5. **No wakeup latency** - spinning threads respond immediately

**Cost:** High CPU usage, variance, and poor behavior under CPU starvation

**SynchronousQueue at 4.78M ops/s:**
1. **Sophisticated dual-mode algorithm** optimized for different scenarios
2. **Some lock-free paths** for fast cases
3. **Parking/unparking** for slow cases to save CPU
4. **Decades of optimization** and edge case handling

**Cost:** Complexity, non-linear performance under edge cases, 32% slower than pure spinning

### What Makes Lock-Based Slow?

**RendezvousChannel at 23.1K ops/s (304× slower):**
1. **Single ReentrantLock** serializes all operations
2. **Three condition variables** require coordination
3. **Park/unpark on every operation** - kernel involvement
4. **Double-block protocol** - producer blocks twice per send
5. **Box allocation** for reference identity

**Each lock operation costs ~43 microseconds** (1/23,100 ops/s)

**UnBufferedChannel at 15.9K ops/s (441× slower):**
1. **All RendezvousChannel costs, plus:**
2. **signalAll() thundering herd** - wakes unnecessary threads
3. **Less optimized coordination** - simpler but inefficient

**Each operation costs ~63 microseconds** (1/15,900 ops/s)

### What Makes Buffering Different?

**ArrayBlockingQueue at 35.4K ops/s:**
1. **Dual locks** (put/take) allow some parallelism
2. **Buffering decouples** producers from consumers
3. **Lock contention still dominates** - can't break 40K ceiling
4. **53% better than RendezvousChannel** shows buffer value

**Buffering helps but can't overcome lock fundamentals**

## The Performance Hierarchy at 4P-4C

### Three Distinct Performance Tiers Emerge

**Tier 1: Multi-million ops/s (lock-free)**
- SpinRendezvousChannel: 7.03M
- SynchronousQueue: 4.78M
- **Characteristics:** CAS-based, high CPU usage, variable latency

**Tier 2: Tens of thousands ops/s (buffered + locks)**
- ArrayBlockingQueue: 35.4K
- **Characteristics:** Dual locks + buffering, balanced tradeoffs

**Tier 3: Low thousands ops/s (rendezvous + locks)**
- RendezvousChannel: 23.1K
- UnBufferedChannel: 15.9K
- **Characteristics:** Single lock + rendezvous, predictable but slow

**Gap between tiers:**
- Tier 1 to Tier 2: ~135× difference
- Tier 2 to Tier 3: ~2× difference
- Tier 1 to Tier 3: ~304× difference

**What this tells us:** Lock-free vs lock-based is the dominant factor. Within lock-based, buffering matters ~2×, but can't close the ~135× gap to lock-free.

## When Balanced Contention Matters

### 4P-4C as the "Stress Test" Configuration

**Why this configuration is revealing:**
- Equal producers and consumers maximizes coordination complexity
- 8 total threads creates real contention on modern CPUs
- Balanced load prevents one side from dominating
- Exposes both throughput ceiling and variance characteristics

**What it reveals:**
1. **Scaling limits** - where does throughput plateau?
2. **Coordination overhead** - how much does algorithm sophistication cost?
3. **Variance patterns** - which designs maintain stability under load?
4. **Lock bottlenecks** - where is the synchronization ceiling?

### Comparing to Other Configurations

**1P-1C shows inherent algorithm costs:**
- No contention, pure overhead measurement
- Lock-based: ~100K ops/s ceiling
- Lock-free: ~5.5M ops/s ceiling

**4P-2C shows imbalance response:**
- ABQ improves (buffering helps)
- SynchronousQueue degrades (coordination struggles)
- Lock-based unchanged (already at ceiling)

**4P-4C shows maximum coordination complexity:**
- Highest variance for SpinRendezvousChannel (20%)
- Lowest throughput for lock-based (lock saturation)
- Best balance for SynchronousQueue (optimized for this)

## Design Principles from 4P-4C Data

### Principle 1: Lock-Free Isn't "Better" - It's Different

**SpinRendezvousChannel:**
- 304× faster than RendezvousChannel
- 5× more variance
- Requires abundant CPU resources
- Degrades gracefully under CPU starvation? **No** - spins waste cycles

**RendezvousChannel:**
- 304× slower than SpinRendezvousChannel
- 5× more stable
- CPU efficient when blocked
- Degrades gracefully under CPU starvation? **Yes** - threads yield

### Principle 2: Sophistication Has Costs

**Simple (SpinRendezvousChannel):**
- Single AtomicReference
- Two spin loops
- ~100 lines of code
- 7.03M ops/s, 12% variance

**Sophisticated (SynchronousQueue):**
- Dual-mode algorithm
- Multiple code paths
- ~1000+ lines of code
- 4.78M ops/s, 8% variance

**32% throughput loss, 33% variance gain** - sophistication trades speed for predictability

### Principle 3: Locks Create a Performance Ceiling

**Observed ceiling: ~15-35K ops/s for lock-based approaches**
- RendezvousChannel optimization: 23.1K
- UnBufferedChannel baseline: 15.9K
- ArrayBlockingQueue with buffering: 35.4K

**Can't break through via:**
- Better algorithms (RendezvousChannel tried)
- More condition variables (doesn't help)
- Buffer decoupling (ABQ tried, only 2× gain)

**Can only break through by eliminating locks entirely**

### Principle 4: Variance Sources Differ by Architecture

**Lock-based variance comes from:**
- Thread scheduling timing
- Wake-up latency variations
- Minor JVM GC pauses

**Lock-free variance comes from:**
- Which threads pair up for handoff
- Cache coherency protocol timing
- CPU scheduler decisions
- More fundamental coordination complexity

**Result:** Lock-free has higher variance ceiling but also higher throughput ceiling
