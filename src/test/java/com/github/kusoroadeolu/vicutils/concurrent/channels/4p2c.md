# Concurrent Channel Benchmarks - 4P/2C

This document analyzes throughput benchmarks for different channel implementations under **producer/consumer imbalance** (4 producers, 2 consumers).

---

## Benchmark Setup

- **JMH version:** 1.37
- **JVM:** Java 25, HotSpot 64-Bit Server VM (25+37-LTS-3491)
- **Benchmark mode:** Throughput (ops/s)
- **Warmup:** 3 iterations × 5s each
- **Measurement:** 3 iterations × 5s each
- **Forks:** 3
- **Thread configuration:** 4 producers (platform threads) / 2 consumers (virtual threads)
- **Queue configuration:** Non-fair mode for ArrayBlockingQueue and SynchronousQueue

## How Imbalance Affects Performance

### Throughput Changes: 4P-4C → 4P-2C

| Implementation | 4P-4C | 4P-2C | Absolute Change | Percentage Change |
|----------------|-------|-------|-----------------|-------------------|
| **SpinRendezvousChannel** | 7.03M | 6.56M | -470K | -6.7% |
| **SynchronousQueue** | 4.78M | 3.36M | -1.42M | -29.7% |
| **ArrayBlockingQueue** | 35.4K | 54.5K | +19.1K | +53.8% |
| **RendezvousChannel** | 23.1K | 22.1K | -1.0K | -4.3% |
| **UnBufferedChannel** | 15.9K | 15.6K | -0.3K | -2.3% |

### What the Data Reveals

**Three distinct response patterns emerge:**

1. **Modest degradation (spin-based, simple):** SpinRendezvousChannel loses only 6.7%
2. **Severe degradation (spin-based, complex):** SynchronousQueue drops 29.7%
3. **Performance improvement (buffered):** ArrayBlockingQueue gains 53.8%
4. **No meaningful change (lock-saturated):** RendezvousChannel and UnBufferedChannel effectively unchanged

## Performance Analysis by Implementation

### SpinRendezvousChannel: Graceful Degradation

**Throughput:** 6.56M ops/s (-6.7% vs 4P-4C)

The minimal degradation tells us:
- Pure CAS operations handle imbalance efficiently
- Extra producers mostly just spin slightly longer
- No complex coordination structures to break down
- Single AtomicReference scales predictably under load

**Variance improvement:** ±240K ops/s (~6% CV) vs ±1.39M (~20% CV) at 4P-4C
- **Fewer consumers = more predictable timing**
- With 4 consumers, handoff patterns vary based on which consumer grabs next
- With 2 consumers, patterns become simpler and more regular
- Suggests variance at 4P-4C came from coordination complexity, not spinning itself

### SynchronousQueue: Imbalance Sensitivity

**Throughput:** 3.36M ops/s (-29.7% vs 4P-4C)

The severe drop reveals:
- Dual stack/queue structure optimizes for balanced workloads
- Internal mode switching (transferer vs dual mode) may thrash under imbalance
- Park/unpark coordination has higher overhead when ratios diverge
- Sophistication comes with edge case costs

**Variance improvement:** ±78K ops/s (~4% CV) vs ±367K (~13% CV) at 4P-4C
- Despite throughput drop, became *more stable*
- Fewer handoff patterns = more predictable behavior
- Suggests internal algorithms stabilize when simpler coordination is needed

### ArrayBlockingQueue: The Imbalance Specialist

**Throughput:** 54.5K ops/s (+53.8% vs 4P-4C)

The massive improvement shows:
- **Buffering decouples producer/consumer rates**
- With 4P-4C: Both sides contend equally on locks
- With 4P-2C: Take-side lock contention cut in half while put-side unchanged
- Net effect: Less total time spent in lock contention

**Why fewer consumers helps:**
- Put lock: Still 4 producers competing (no change)
- Take lock: Only 2 consumers competing (50% reduction)
- Buffer allows producers to make progress independently
- Non-fair mode lets fast paths dominate

**Variance:** ±1.6K ops/s (~6% CV) - consistent with 4P-4C
- Lock contention patterns simply shifted, not eliminated
- Stable variance suggests predictable behavior despite imbalance

### RendezvousChannel: Imbalance-Agnostic

**Throughput:** 22.1K ops/s (-4.3% vs 4P-4C)

The stability across configurations reveals:
- Performance is **dominated by single-lock bottleneck**
- Thread count and distribution barely matter
- Already operating at lock saturation ceiling
- Triple condition variable overhead constant regardless of load shape

**Variance:** ±810 ops/s (~4% CV) - lowest absolute variance
- Lock serialization eliminates most timing variability
- Each operation waits its turn in predictable sequence
- Fairness through forced serialization

### UnBufferedChannel: Also Lock-Saturated

**Throughput:** 15.6K ops/s (-2.3% vs 4P-4C)

Similar pattern to RendezvousChannel but lower baseline:
- `signalAll()` overhead dominates performance profile
- Imbalance irrelevant when every operation is already expensive
- Thundering herd effects consistent regardless of thread distribution

**Variance:** ±1.9K ops/s (~12% CV) - higher than RendezvousChannel
- Less precise signaling creates more timing variability
- Multiple threads waking unnecessarily adds unpredictability

## Variance Analysis: Imbalance Effects on Stability

| Implementation                     | 4P-4C CV | 4P-2C CV | Stability Change |
|------------------------------------|----------|----------|------------------|
| **RendezvousChannel**              | ~4% | ~4% | No change |
| **SynchronousQueue**               | ~13% | ~4% | **Improved 9%** |
| **SpinRendezvousChannel**          | ~20% | ~6% | **Improved 14%** |
| **ArrayBlockingQueue(1 capacity)** | ~6% | ~6% | No change |
| **UnBufferedChannel**              | ~7% | ~12% | Degraded 5% |

**Key finding:** Spin-based approaches become *significantly more stable* with fewer consumers, while lock-based approaches maintain consistent variance.

**Why this happens:**
- Fewer handoff partners = fewer timing variations
- Simpler coordination patterns = more predictable execution
- Locks already serialize operations, so thread count less relevant to variance

## Architectural Insights from Imbalance Testing

### What Makes SpinRendezvousChannel Resilient?

**Simplicity under pressure:**
- Single AtomicReference has no modes or states
- No internal algorithms that optimize for specific ratios
- Degradation is linear: more waiting = proportionally less throughput
- No structural breakdown as load patterns change

### What Makes SynchronousQueue Vulnerable?

**Complexity under edge cases:**
- Dual-mode design (stack vs queue) optimized for balanced loads
- Mode transitions may oscillate under imbalance
- Park/unpark coordination has fixed overhead that becomes proportionally larger
- Sophistication optimizes common case but hurts edge cases

### What Makes ArrayBlockingQueue Thrive?

**Buffering decouples contention:**
- Producers and consumers use separate locks
- Imbalance naturally reduces contention on less-active side
- Buffer allows temporary rate mismatches
- Each side's contention independent of the other's thread count

### What Makes Lock-Based Channels Immune?

**Already at performance floor:**
- RendezvousChannel: Single lock serializes everything
- Performance ceiling determined by lock overhead, not thread patterns
- Imbalance can't make a bottleneck worse when it's already maximally saturated
- Consistent ~22K ops/s suggests this is the "speed limit" for lock-based rendezvous

## Design Lessons from 4P-2C Data

### Lesson 1: Simplicity Scales Differently Than Sophistication

SpinRendezvousChannel's 6.7% degradation vs SynchronousQueue's 29.7% degradation demonstrates that:
- Simple designs degrade gracefully and predictably
- Complex optimizations have non-linear failure modes
- Edge cases punish sophistication more than simplicity

### Lesson 2: Buffering Transforms Imbalance Impact

ArrayBlockingQueue's 53.8% improvement shows:
- Decoupling producers from consumers changes everything
- Imbalance becomes an *advantage* when it reduces contention
- Single-capacity buffers (rendezvous) forced to handle imbalance; multi-slot buffers embrace it

### Lesson 3: Variance Behavior Differs by Architecture

The CV improvements for spin-based (14-20%) but not lock-based (<1%) reveal:
- Spin approaches: Variance comes from coordination complexity
- Lock approaches: Variance comes from serialization timing
- Fewer partners = less coordination complexity, but lock timing unchanged

### Lesson 4: Performance Floors vs Ceilings

Lock-based channels at ~22K ops/s regardless of configuration suggest:
- There's a fundamental "lock speed limit"
- Below this limit, optimizations don't matter
- Above this limit (spin-based), architecture choices matter enormously

### Lesson 5: Imbalance Tests Reveal True Characteristics

4P-2C configuration exposed:
- Which implementations optimize for balanced loads (SynchronousQueue)
- Which are architecture-agnostic (SpinRendezvousChannel)
- Which benefit from asymmetry (ArrayBlockingQueue)
- Which are already bottlenecked (RendezvousChannel, UnBufferedChannel)

## Practical Implications

### When Imbalance is Expected

**If producer count >> consumer count (or vice versa):**
- ArrayBlockingQueue: Use multi-slot buffer to smooth rate differences
- SpinRendezvousChannel: 6.7% tax on throughput is predictable and acceptable
- SynchronousQueue: 30% degradation may be unacceptable
- Lock-based channels: Performance unchanged, so viable if throughput sufficient

### When Variance Matters More Than Peak Throughput

**For latency-sensitive applications:**
- Consider that imbalance *improves* spin-based variance (20% → 6%)
- Lock-based channels maintain their ~4% consistency
- Fewer consumers might actually improve tail latencies for spin approaches

### When Architectural Simplicity is Valued

**For maintainability:**
- SpinRendezvousChannel's graceful degradation pattern is predictable
- SynchronousQueue's non-linear response harder to reason about
- Lock-based consistent behavior (if slow) easier to capacity plan
